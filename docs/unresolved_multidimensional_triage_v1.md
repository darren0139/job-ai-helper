# Multidimensional unresolved triage V1

## Route-drift audit correction

The original preview is preserved as a historical diagnostic artifact. See
`docs/unresolved_multidimensional_route_audit_v1.md` and the final route-audit
preview for the corrected proposals. Neither V3 recommendations nor diagnostic
proposals are human gold.

Primary selection now distinguishes a bounded existing predicate observation
from registry co-occurrence. Exact existing terms with an optional final plural
are recorded as diagnostic observations; no stemming or synonym expansion is
used. All existing conjunctive requirements must be present. Custom evidence
policies (including C/C++ boundaries) are never replaced by this observation.
An existing term alone does not establish a primary capability blocker: a bounded
current activity is also required. Exclusions remain visible and human review is
required; these observations supply no evidence credit or native resolver answer.

Technologies in other raw-parent sentences remain source-tagged candidates but
cannot drive a relationship for the current sentence. Bare OR and unavailable
native structure are independent observations, not automatic structural failure.
Recorded loss of parent activity and the specifically unrepresented open language
alternatives remain defensible structural investigations. Complete grounded
Azure-familiarity wording can propose TECH_ID while native resolution stays
unresolved. Unknown ROS identity is never assigned an invented registry ID.

New route reasons, predicate-observation outcomes and familiarity statuses are
diagnostic output only. Exclude them from any future model prompt alongside all
other primary/remediation/review outcomes; only immutable definitions and bounded
source context may form a separately approved input contract.

Schema: `unresolved-multidimensional-triage-v1`. This is an additive report, never
a Job Match input, canonical parser, scoring engine or publication producer.

Reuse: `unresolved_adjudication.load_occurrences/build_input` owns the original
canonical selection and bounded candidates; `unresolved_source_review.recover`
owns hash-pinned source verification; `list_latest_job_match_corpus_snapshots`
reads the DB with mode=ro. Production resolver, `technology_identity_scope`,
`technology_requirement_structure`, registry, taxonomy and governed contextual
`context` remain their existing owners. Maintenance supplies unchanged versions.

One primary route is recorded with PROPOSED/NEEDS_REVIEW status. It may remain
undetermined. The two original NAC controls retain inherited status without a new
reviewer/date. No V3 route/rationale is used to build route truth or human labels.
The handover/V3 fingerprints are checked as provenance, not gold authority.

Technologies are exact registry alias candidates, separately from full native
resolution; an unverified mention has no invented technology ID. Activity spans
are exact bounded lexical observations, not equivalent capabilities. Parent
activity requires independently verified source context. Source structure cues
are explicitly proposed observations, alongside untouched native structure.
They never consume text, mint children, assign weights or repair production scope.

Every recorded parent ID, allocation fraction and atomic flag is copied. Candidate
capabilities are exact existing IDs with existing predicates/exclusions and a
TOKEN_OVERLAP_ONLY_NOT_EQUIVALENCE warning. Secondary tags are nonexclusive
diagnostics, not additional routes, scored requirements or approved mappings.

Java web development can propose relationship investigation while the native
relationship predicate remains NO_RELATIONSHIP_JUSTIFIED. Python/Node.js remain
recognized candidates under open one-or-more examples; no mandatory children.
MongoDB/Elasticsearch recognition does not establish Redis recognition or schema
design. Responsive React UI retains its shared parent allocation. Case #32 remains
DEFERRED_FOR_CURRENT_BENCHMARK, with HIGH_PRIORITY_INVESTIGATION for parent fidelity;
the parent-only UI activity is not fair child-only gold.

Run explicitly, with new output paths:

```powershell
$env:PYTHONDONTWRITEBYTECODE='1'
$env:LITELLM_LOCAL_MODEL_COST_MAP='True'
$env:CAPABILITY_RAG_MODE='off'

```

The CLI defaults to the same 40 IDs; `--job-id`/`--limit` only narrow selection.
It hashes protected inputs before/after. A whole live DB hash difference triggers
read-only cited-record verification, not a claim of database byte immutability.

## Future model contract — design only

Proposed future prompt/input/output versions: `unresolved-context-routing-prompt-v2`,
`unresolved-context-routing-input-v2`, `unresolved-context-routing-output-v2`.
No provider or prompt execution is implemented here. V1 prompt/schema/gate and
both frozen manifests remain unchanged.

An explicit future allowlist may include bounded exact current requirement text,
native structure diagnostics, registered technology IDs/aliases, bounded existing
taxonomy predicates with complete exclusions, and source-grounded parent excerpts.
Parent excerpts require a separately versioned context-aware selection/input
fingerprint and independent human review. Never append them to frozen V1 inputs.
Apply the existing privacy checks to every allowed excerpt and reject oversize or
sensitive data rather than silently truncating meaningful exclusions/context.

Never send this report wholesale. Exclude primary proposals, remediation,
human-review status/receipts, NAC expectations, original review buckets, V3 labels,
V3 rationales, suggested candidate outcomes, gold answers, full sensitive JDs,
resume/profile evidence, credentials and secrets. Technology candidates and taxonomy
definitions are knowledge context, not evidence that an applicant possesses skills.

Future output must be exact structured JSON: one proposed route or UNKNOWN,
independent technology/activity/structure axes, supplied IDs only, exact source
spans, finite confidence, bounded arrays and explicit missing-context indicators.
Validate duplicate keys, identity, schema, ID membership and span grounding using
existing strict adjudication validation patterns. Invalid/ambiguous outputs fail
closed to UNKNOWN; no output may mutate scoring or knowledge.

The next human decision is whether these diagnostics and a separately frozen
context-aware benchmark are acceptable. Human route receipts, a live benchmark,
and any parser/identity/relationship/predicate production correction require
separate authorization, targeted regressions and scoring replay. No global
SQL→querying, AWS→architecture, Node.js→API, C#→backend, JavaScript→frontend or
MongoDB→schema mapping is authorized.
