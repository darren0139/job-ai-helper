## Which exact partial-action conditions qualify for WEAK?

### Recommended for approval: P3

An incomplete coordinated AND requirement may have an **eligible WEAK ceiling** only if:

1. Its grounded JD is within the reviewed finite software-artifact grammar. Its mandatory
   actions are design, creation (develop/build) and maintain or deploy. Optional preferences
   are not converted into mandatory duties, and alternatives are not rewritten as AND.
2. One verified original project/experience record affirmatively attributes **both design
   and creation** to the candidate on the same required artifact. Build/develop/implement
   equivalence is limited to affirmative creation of that bound software artifact; it does
   not imply endpoint authorship from API consumption or integration.
3. Those two actions each have **full required technical-object/modifier support**. A family
   reference such as `cloud applications` does not prove large-scale data processing or
   deployment. Ownership of an artifact family alone never bypasses missing technical scope.
4. Only the required lifecycle responsibility remains absent. It is not supplied by usage,
   another object, a team/vendor statement, a future plan, or a separate source record.
5. No requested responsibility is explicitly denied or contradicted in the record and no
   unresolved subject/modality/attribution ambiguity remains. The proposed exception for an
   explicitly denied missing action is deliberately **not approved** here.
6. The native scorer already supplies positive credit under its existing source and
   capability constraints. The result is a downward ceiling: DIRECT/TRANSFERABLE -> WEAK,
   WEAK -> WEAK, NONE -> NONE. The existing numeric WEAK value stays **0.20**.
7. Existing specific policies still bind. API-bearing backend evidence must independently
   satisfy the existing API authorship evaluator. The general rule never turns PostgREST,
   Supabase integration or client consumption into an authored receiving endpoint.

This is **not two-of-three scoring**. Design+maintenance without creation does not
qualify; creation+maintenance without design does not qualify under P3 either. Design
and creation are designated as the reviewed upstream pair that directly addresses these
explicit design/build responsibilities. Missing lifecycle experience is still recorded;
WEAK does not certify the full obligation. This is a bounded proposed contract, not a
claim that design is universally more valuable than maintenance or implementation.

No universal action percentages, new action weights or altered WEAK numeric values are
introduced. An eligible record can still receive native NONE because its capability is
not supported (notably full-stack topic requirements). Eligibility and credit are separate.

### Rejected for automatic approval

- P1: maintenance-only, design-only or creation-only experience receiving WEAK merely
  because it is one requested action. This is conservative relative to unchecked DIRECT,
  but does not justify a generally transferable positive credit contract.
- Arbitrary action-count fractions, treating any two duties identically, or awarding
  WEAK for generic software experience, ESP32/GPIO topics, tool usage, API consumption,
  wrong-object actions or unverified source/evidence IDs.
- Restoring DIRECT through recovery when any mandatory action or technical scope is
  unproved. A zero-overlap topic match is not an ownership receipt.
- Upgrading native NONE to WEAK solely on detected partial ownership, lifting native
  capability caps, or giving a partial record priority over an admissible complete one.
- Combining separate partial bullets, treating multiple API sources as one authored
  activity, substituting maintain for deploy, or treating optionality/OR as mandatory AND.

### Still unresolved / review-only

- P2's creation-plus-lifecycle pair when design is absent. This has a coherent delivery
  interpretation and is preferable to a raw action-count rule, but expands the recommended
  partial contract beyond the design/creation pair. Meaningful experience can remain
  under-credited under P3; the report does not declare it irrelevant.
- Explicitly denied **missing** lifecycle responsibility with independently proven design
  and creation. The evidence can logically prove those two actions without claiming the
  third. The detector retains that proof, but every candidate policy defers the label;
  omission versus explicit denial otherwise creates a fairness asymmetry that needs a
  reviewed exception rather than an automatic silent reward or penalty.
- Related artifact-family ownership with omitted JD technical modifiers; rich paraphrases,
  pronouns with multiple antecedents, mixed agents, mixed AND/OR, unsupported negative JD
  grammar and any scope that deterministic language rules cannot bind safely.

`REVIEW_REQUIRED` is an offline decision disposition with a null effective label, never
a production score label. A reviewed native NONE may remain NONE; uncertain positive
credit is not silently converted into a numeric zero or a new WEAK tier.

## Two evidence dimensions and bounded language extension

The new research helper leaves the Stage 2C detector unchanged. It reports separately:

- `supported_actions`: affirmative ownership on the appropriate artifact family.
- `technical_supported_actions`: actions additionally tied to the full required literal
  object/modifier scope.
- `ownership_complete`: all mandatory actions (or the admitted alternative) owned.
- `complete`: all mandatory actions **and** full required technical scope proven.

First-person passive `OBJECT were designed, developed and maintained by me` is admitted
only with the reviewed finite verb list and explicit `me/myself` agent. Vendor/team/us/
third-party agents do not prove candidate ownership. Relative `Used OBJECT which I
designed, developed and maintained` is admitted with explicit first-person subject and
reviewed past-tense actions. `which we`, vendor clauses, future intent and unsupported
bindings do not become ownership. Multiple clauses may contribute only inside the same
verified source record; independent bullets remain independent.

Shortened heads allow family-level proof for reviewed forms such as embedded software
(modules), data pipelines, full-stack applications, cloud(-based) applications and
backend services (and API). Missing qualifiers remain unproved. Full technical support
still requires the original complete object scope, with only the previous bounded case/
punctuation normalization. No RLS implementation, technology expertise, protocol or API
authorship is inferred. Action/object character spans refer to the original evidence.

An explicitly single-artifact `Developed ... but did not maintain it` binding records
the denial. It does not erase creation ownership or manufacture technical modifiers;
it prevents automatic partial credit pending review. Same-object contradictory activity
cancels that action's affirmative ownership. Unsupported grammar stays review-only.

## Actual native path, selection and recovery

The research wrapper reuses cloned native functions and the original compatibility
predicate. It adds only eligibility restrictions and downward label ceilings; there is
no new similarity sorter or unrelated selector.

1. Build deterministic keyword proposals from eligible records; preserve ordinary native
   keyword/link/structured/validation behavior. Raw keyword DIRECT is a preliminary
   retrieval proposal, not an effective full-obligation evidence award.
2. Evaluate the complete admissible candidate pool **first**. If one complete source exists,
   use native selection on that pool and retain native capability ceilings. A high-overlap
   partial first bullet cannot suppress an otherwise eligible complete second source.
3. Only if no complete source is admissible, evaluate that policy's partial pool through
   the same native selectors. Apply the proposed WEAK ceiling after linking, structured
   matching, validation, single-row reselection, capability caps and NONE recovery.
4. A partial pool has an additional floor guard: if the unchanged native pipeline's final
   result for the original inputs was NONE, every partial capped result stays NONE. Thus
   action recognition alone cannot create recovery credit. Complete-source selection is
   distinct: its native capability and source ceilings remain authoritative.
5. Recheck the original evidence ID, source, text and section at label-writing boundaries;
   after recovery, apply the final invariant before interpreting synthetic contribution.
   Every label adjustment has an attributable decision receipt and research policy ID.

The JSON includes raw keyword proposals; linked/structured/validated/reselected/capped/
recovered/final labels; compatibility events; source/evidence continuity; and native
recovery receipts. All five existing capabilities retain their current reselection opt-in
settings. A stage can be invoked without its replacement loop activating; no extra opt-in
or native ceiling was fabricated. Existing API reselection tests remain in the focused run.

"Native NONE" in the ceiling table means the unchanged native **final** label, not merely
an initial missing keyword. Existing governed semantic recovery can still change an initial
lexical NONE for a valid source; this proposal adds no recovery permission. A topic-only
ESP32 record has no action proof and remains ineligible even when native firmware recovery
would yield DIRECT. Partial native WEAK is only retained or capped, never created from
native final NONE. The explicit initially-missing-keyword controls distinguish these paths.
